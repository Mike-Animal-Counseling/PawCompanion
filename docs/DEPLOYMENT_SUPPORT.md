# Deployment support

The application is deployment-ready as a **single same-origin container**: Express serves the API, the Vite build, `/uploads`, `/sounds` and the PWA. That keeps the refresh cookie first-party and avoids Vercel/Render cross-site cookie problems.

Recommended stack:

```text
Render Web Service (Docker)  →  one HTTPS URL
        │
        └── MongoDB Atlas M0
```

`render.yaml` and `Dockerfile.render` are already in the repo.

## What I need from you

Only two things are required for a public demo:

1. **Render account** with this GitHub repo connected (or a Render API key).
2. **MongoDB Atlas connection string** for a demo database.

Optional:

- a custom domain
- Upstash Redis URL (`rediss://…`) for shared rate limits
- Hugging Face API key if you want hosted AI instead of the local persona fallback

Do not paste secrets into chat or commit them. Enter them in Render's environment UI, or provide them through a secret manager.

## Render setup

1. Render → New → Blueprint → connect `Mike-Animal-Counseling/paw-companion`.
2. It reads `render.yaml` and creates `paw-companion-demo`.
3. Set `MONGO_URI` to the Atlas URI (secret).
4. `JWT_SECRET` is generated by Render.
5. Deploy.

Expected URL:

```text
https://paw-companion-demo.onrender.com
```

Render may add a suffix; use the exact URL it shows.

Health check:

```text
GET https://paw-companion-demo.onrender.com/api/health
```

The first boot runs the seed because `SEED_DEMO=true`. Every restart/reseed resets the demo data. Uploads are ephemeral on the free plan.

## MongoDB Atlas

1. Create a free **M0** cluster.
2. Create a database user with a strong password.
3. Network Access: allow Render. For a throwaway demo, `0.0.0.0/0` is acceptable; restrict it for anything real.
4. Copy the SRV URI and append the database name:

```text
mongodb+srv://USER:PASSWORD@CLUSTER.mongodb.net/pawcompanion?retryWrites=true&w=majority
```

5. Put it in Render as `MONGO_URI` (secret).

## Environment variables

### Required for the Render demo

| Variable | Value |
| --- | --- |
| `NODE_ENV` | `production` |
| `HOST` | `0.0.0.0` |
| `PORT` | `5000` |
| `MONGO_URI` | Atlas SRV URI (secret) |
| `JWT_SECRET` | Render `generateValue: true` |
| `PAYMENTS_MODE` | `sandbox` |
| `ALLOW_SANDBOX_PAYMENTS` | `true` (demo only) |
| `SEED_DEMO` | `true` |
| `ALLOW_SEED_IN_PRODUCTION` | `true` (demo only) |
| `ENABLE_AI` | `false` |
| `DEMO_MODE` | `true` |

`RENDER_EXTERNAL_URL` is provided automatically and used as `APP_URL` + `CORS_ORIGIN`. Do not set `APP_URL`/`CORS_ORIGIN` to localhost.

### Optional

| Variable | When |
| --- | --- |
| `REDIS_URL` | `rediss://…` for shared rate limits across instances |
| `HUGGINGFACE_API_KEY` | only if `ENABLE_AI=true`; set provider budget limits |
| `HF_CHAT_MODEL` / `HF_ROUTER_MODEL` | only with a provider key |
| `TRUST_PROXY` | `1` behind Render's proxy |
| `LOG_LEVEL` | `info` |

### Not used in this build

- Stripe/live payment keys: payments are sandboxed. Do not add live keys until the payment provider is implemented.
- Email/SMS provider keys: not implemented.
- Object storage keys: uploads use local disk for the demo.

## Separate Vercel + Render option

If you prefer Vercel for the frontend:

- Deploy `frontend/` to Vercel (`npm run build`, output `dist`).
- Deploy `backend/` to Render as a separate API.
- Set `VITE_API_URL` to the API URL, or proxy `/api` through Vercel.
- The refresh cookie is `SameSite=Lax`; put both on the same registrable domain or use a same-origin rewrite. `*.vercel.app` + `*.onrender.com` alone will break refresh.

For this project, the single Render container is simpler and is what `render.yaml` configures.

## Verification after deploy

```bash
curl -fsS https://YOUR-URL/api/health
curl -fsS https://YOUR-URL/api/ready
curl -fsS -o /dev/null -w '%{http_code}\n' https://YOUR-URL/
```

Then run the browser smoke test against the deployed URL:

```bash
E2E_BASE_URL=https://YOUR-URL npm run e2e
```

Demo accounts are the same seeded accounts in the README.
